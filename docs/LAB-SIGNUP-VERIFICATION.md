# Laboratory signup verification

Choose a role on `/join`. Laboratory signup confirms a work mailbox through the existing hashed, expiring, single-use email sign-in link, then opens `/dashboard/laboratory`. The initial application is one four-stage multipart form including an ISO/IEC 17025 scope PDF. It supplies the lab identity in the same transaction, so a second organization-details form is unnecessary. Incomplete and pending accounts can prepare private drafts and use the sandbox; they cannot issue production credentials or publish a lab profile.

The server requires the signed-in, confirmed email-auth identity, a matching laboratory website domain, accredited status, accreditation body, certificate number and public register URL. Common free-webmail domains are refused. Matching a domain never grants authority: ICS must verify lab identity, the current certificate and requested scope against the accreditation body's public register. The reviewer records the lookup URL, result and date; these are stored in the check evidence and audit. The blocklist is a conservative screening aid, not a complete directory of every webmail provider. Human identity/register review remains mandatory.

A first independent ICS admin records identity, accreditation and scope checks. A different independent ICS admin reviews those materials and records final approval. Neither may be an applicant owner, member, submission actor or contact. Both user IDs and normalized email identities must differ. The first reviewer's current ICS-admin eligibility is rechecked at final approval. Existing Ed25519 key-control and signing-conformance checks remain required. The lab sees four progress steps: confirmed work email, identity/accreditation/scope, key challenge and independent ICS review. Historical applications without the current submission gate require a replacement application before approval.

Application submission and each final status decision write an audit event and a local organization notification in the same D1 batch. Scope files are private R2 objects; failed application transactions remove the staged file. Decision events and notices have deterministic identities to prevent duplicate successful decisions. No email transport is added for decisions.

## Review and release limits

This is a draft on main, independent of existing security drafts. It overlaps `lib/tec.ts` and `lib/issuer-verification.ts` in #31/#32; integrate semantically after the ordered security review, preserving both sets of guards. #26's session-only authentication, #29's role checks and #31's production key restrictions remain separate unmerged security prerequisites. This change does not activate, merge or reproduce the security stack. Do not infer a secure production system from these local checks.

An operator must separately attest that `ICS_ADMIN_EMAILS` names at least two distinct humans who have no lab association. Live configuration and membership data were not accessed. Register checks are performed by authorized reviewers; this runner did not contact a register or verify a real laboratory. Receiver remains OFF; Security E2E and F05 remain open. No deployment, migration, production row query, credential configuration or real message was performed.

Validation uses disposable D1/R2, synthetic accounts, ephemeral test signing keys and intercepted email transport. The unmodified-main baseline passed 73 unit tests. The draft passed 91 unit/backend/UI tests and 29 compiled Worker/rendered/redirect checks, plus production build and focused source lint. Typecheck remains limited: main had 63 diagnostics; this draft has 58 and no new normalized diagnostics. The inherited email-auth test file also retains six pre-existing lint findings. Local browser review confirms role-first signup and laboratory-domain fields; real email delivery and live reviewer identities are not claimed.

The four-reviewer local amendment tests all six pairs of four synthetic configured reviewers. Each pair passes only after a different second reviewer signs off; the same reviewer twice, a normalized mailbox with a different user ID, a repeated user ID, an applicant on the configured list, and a first reviewer who later joins the applicant cannot count. Empty or absent `ICS_ADMIN_EMAILS` grants no admin access. Its parser expects comma-separated mailbox identifiers, trims whitespace and normalizes case. No real approver addresses or configuration values are in these fixtures. Original candidate commit and patch remain preserved; this amendment is an ordinary child commit with no application-source change.
