# Mint latency and acknowledgment

Order TECRID-MINT-TO-PHONE-1, step 5. The initial dispatch targets are under 60 seconds from issuance to phone push service acceptance and to recipient webhook acceptance. The brand dashboard shows minted, queued, delivered and acknowledged times for the latest 20 routed records and 80 events. It displays measured latency, overdue events, retries and missing channels. Channel destinations and secrets are withheld from the brand timeline. Controlled result values do not appear in it.

Successful write responses wake the outbox using Worker waitUntil when enabled. Routing jobs and notifications are durable; five transports run concurrently with 10-second request timeouts. A registered scheduler or protected worker call is needed for idle-time recovery and sustained backlog. Provider outages, throttling and large backlogs can exceed the target. No scheduler or automatic delivery is activated by this PR.

Delivered records transport acceptance. A push link contains only event/channel IDs in its authenticated dashboard URL. Loading that explicit link while signed in acknowledges that owned channel/event. An unauthorized user cannot acknowledge it. Webhook consumers use the HMAC acknowledgment contract in docs/VLE-DELIVERY-CONTRACT.md. Plain provider acceptance never implies a viewed alert. If sign-in loses the original link parameters, no click acknowledgment is inferred.

The full Worker test creates synthetic laboratory, brand, certifier, marketplace and GATED retailer identities in isolated D1. It issues a cryptographically signed controlled credential through the built API, decrypts intercepted RFC8291 VAPID push, validates both scoped webhook HMACs, checks the GATED organization has no snapshot and no network request, measures latency, and records explicit acknowledgments. No production registry, real provider, phone, recipient or account is used. The test uses an isolated registry here; step 6 adds the production API's enforced sandbox key tier.

This end-to-end test also exposed a runtime interoperability issue: Node's exported JWK can label its Ed25519 algorithm as Ed25519, while Workers expects the RFC 8037 EdDSA alias. Verification normalizes only that alias during key import. Stored JWKs, old credential canonical payloads, signatures and fingerprints are unchanged. The same Ed25519 verification remains mandatory. See the [Cloudflare Web Crypto API](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/) for supported operations.
